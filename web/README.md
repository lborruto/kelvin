# Kelvin web

SvelteKit (Svelte 5) PWA, built as a static SPA and served by the backend in production.

## Develop

    # terminal 1 — the backend in simulator mode
    cd backend && KELVIN_FAKE=1 KELVIN_DATA=/tmp/kelvin-dev uv run uvicorn --factory kelvin.api.app:create_app --port 8000
    # terminal 2 — the UI with hot reload, proxying /api to :8000 (override with KELVIN_API)
    cd web && npm ci && npm run dev

Kelvin asks for a login. In simulator mode (`KELVIN_FAKE=1`) the account is
`demo@kelvin.local` / `kelvin`; the first login on a fresh `KELVIN_DATA` makes it the home's account.

## Check

    npm run check        # svelte-check
    npx vitest run       # unit and component tests
    npx playwright test  # end-to-end against the simulator (builds, then starts the backend serving the build)

The end-to-end suite runs a phone (Pixel 7) and a desktop project in Chromium, on port 4174 with
its data in `/tmp/kelvin-e2e`, through `python -m kelvin` like the Docker image. If Playwright
asks for a browser: `npx playwright install chromium`. A `setup` project logs in through the
login screen first and shares the session (`e2e/.auth/state.json`, gitignored) with the others.

The default suite runs French (an `fr-FR` browser); `e2e/english.spec.ts` runs the key flows in
English, and `e2e/layout.spec.ts` checks the layout in both languages.

`npx playwright test` also starts a second simulator on port 4175 with a fresh `KELVIN_DATA`
(`/tmp/kelvin-e2e-brands`). Parallel worktrees move them with `KELVIN_E2E_PORT` (main simulator,
4174), `KELVIN_E2E_BRANDS_PORT` (4175) and `KELVIN_E2E_DATA` (`/tmp/kelvin-e2e`, the brands one is
its `-brands` sibling). The `brands` project logs in choosing « Atlantic Cozytouch » and runs
`e2e/brands.spec.ts` on the Atlantic house. With an external Kelvin (`KELVIN_E2E_URL`) it runs only
if `KELVIN_E2E_BRANDS_URL` points at a fresh simulator (empty `KELVIN_DATA`).

Screenshots (simulator only): `SCREENS=1 npx playwright test screens` writes them to
`test-results/screens/` as `<locale>_<project>_<page>.png`; set `SCREENS_DIR` to write
elsewhere and `SCREENS_LOCALE=en` for English.

## Components

Grid and tariff pieces (`src/lib/components/`): `GridChips` (Énergie's context row; Tempo only when the
API sends `tempo`), `TempoDot` (the only user of the `--tempo-*` tokens), `SourcesList` (Réglages ›
Sources de données), `TariffForm` (option, dated prices, seasonal off-peak hours, Tempo hours and prefill; the
document logic is in `src/lib/tariff.ts`), `TempoRows` (the six colour rows under Tempo) and
`HcHpPanel` (Base, HC/HP or Tempo). Under Base the Énergie bars draw one « Consommation » series and
the Heures creuses card says there are none.

Weather pieces (Plan 14): `settings/PlaceSearch` (an APG combobox over `POST /api/weather/search`),
`settings/WeatherPanel` (Réglages › Météo: the place, the coordinates form, « Supprimer »), the store
`$lib/stores/weather.svelte.ts` (the snapshot's and SSE's `weather`, the hourly cache per window and
place) and the words in `$lib/weather.ts`. Nothing about weather shows without a place.

## Languages and paths

- Messages live in `src/lib/i18n/fr.ts` (the source) and `en.ts` (typed from it); components read
  `m.area.key` from `$lib/i18n`, in templates or `$derived`, never at module scope. Plurals use
  `Intl.PluralRules`; numbers and dates come from `$lib/format` in the active language (English
  is en-GB; both use 24 h and Paris time).
- The language: a choice stored in `localStorage['kelvin-locale']` wins; else French when any
  browser language is French; else English when the browser names a language; else French.
  `app.html` sets `<html lang>` before the app boots. The choice is made in Réglages › Affichage ›
  Langue or on the login screen (FR | EN); switching never reloads.
- Backend errors and pending labels arrive as codes (`src/lib/i18n/api-codes.json`, generated by
  `backend/scripts/export_codes.py`) and are translated by `src/lib/i18n/codes.ts`; the server's
  French `detail` is the fallback for an unknown code.
- The PWA manifest cannot vary by user: it stays French (`lang: 'fr'`).
- Paths are English: `/` (rooms), `?sheet=<id>` on any page (the room sheet; `/rooms/[id]` redirects to `/?sheet=[id]`), `/schedule`, `/energy`, `/home`, `/home/devices` (rooms and
  devices: the device tree reloads from memory every 30 s; setup writes and the sync come through
  SSE `pending` and `layout`, and a confirmed write offers « Annuler » for 10 s), `/login`, with
  the Home anchors `#away`, `#tariff`, `#linky`, `#alerts`, `#sessions` and the Energy anchors `#quality`, `#curve`. The
  old French paths and anchors are rewritten before boot by `app.html` and by `canonical()` in
  `src/lib/paths.ts`, whose tables the tests keep equal (this README names no French path:
  `scripts/check-paths.mjs` scans it).
- Alerts and sessions: the backend sends kinds and params only (`GET /api/alerts`, the SSE `alerts`
  event); `alertText` (`src/lib/alerts-text.ts`) writes the words from both dictionaries, so a new kind
  needs its `alertText` case and its two messages. `AlertCallout` shows the screen's own kinds
  (Energy, the room), Home lists them all; the store follows the stream and dismisses through
  `POST /api/alerts/{id}/dismiss`. `SessionsPanel` (Home › Settings) lists `GET /api/sessions` and
  signs devices out; a 404 `session_unknown` just removes the row.
- Checks: `node scripts/i18n-check.mjs [--strict]` lists hard-coded French, unused keys and
  messages read at module scope (a line that must keep a French literal is marked
  `// i18n-ignore: <why>`); `node scripts/check-paths.mjs` lists French paths; both also run
  inside `npx vitest run`.

## Serve the build from the backend

    npm run build
    cd ../backend && KELVIN_FAKE=1 KELVIN_DATA=/tmp/kelvin-dev KELVIN_WEB=../web/build uv run python -m kelvin

Then open http://127.0.0.1:8000. Against your own home, drop `KELVIN_FAKE=1` and use a real
data directory (`KELVIN_DATA=./data`).

The version shown on Maison comes from `package.json`. Icons are rendered from
`static/icon.svg` by `npm run icons`.

## Énergie CSV export (machine contract)

Énergie's export menu (« Exporter » in the page header, « ⋯ » on a phone, and the « Exporter (CSV) » button at the
end of the page; the actions are `src/lib/export.ts`) builds the files in the browser from the JSON the page shows (no server
endpoint), so every figure is the one the page shows for the same bar or half-hour, at the API's
precision: a day's € are the same in whatever period it is exported. Every file is UTF-8 with a
BOM, CRLF line ends, no thousands separator, and follows the UI language for its number format:
in French `;`-separated with `,` as the decimal separator (the French spreadsheet convention, so a
French Excel or LibreOffice opens it with numbers as numbers), in English `,`-separated with `.`
as the decimal separator (a text cell holding a `,` is quoted). The examples below are the French
format. Timestamps are in ISO 8601 Paris local time with their offset
(`2026-10-25T02:30:00+01:00`, so the repeated autumn hour stays unambiguous), and a missing value
is an empty cell (never 0). Headers and file names stay French in every locale. Text cells that start with `=`, `+`, `-`, `@`, a tab or a CR are prefixed with `'`. No
PDL, token, email or id is exported; rooms and radiators appear by name.

- `energie_<from>_<to>_<group>.csv` (`<to>` exclusive) — one row per bar of the selected period
  (with Linky, the buckets before the first counted one — Linky data, or a counted day without it, which pays its subscription — are not bars, and not rows), then a
  `total` row (the hero's figures):
  `periode;debut;fin;maison_kwh;hc_kwh;hp_kwh;split_estime;radiateurs_kwh;radiateurs_interp;reste_kwh;energie_eur;abonnement_eur;total_eur;prix;jours_manquants;radiateurs_jusqu_au;radiateurs_couverture;dehors_moy_c;dju_base18;meteo_jours`.
  kWh have 3 decimals, € 2; `split_estime` and `radiateurs_interp` are `1`/`0` (radiator energy
  spread between two readings counts as estimated); `prix` is `hc=0,2068|hp=0,2700`, or, when a bar
  used several price rows, each prefixed with its date and separated by a space.
  The radiator figures count elapsed days only: `radiateurs_jusqu_au` (`YYYY-MM-DD`, empty without a
  radiator sum) is the last day they count, the row's last day for a past row, yesterday for a row
  running into today (`debut`/`fin` stay the row's whole span, so a running month's total reads
  `fin` = the next 1st and `radiateurs_jusqu_au` = yesterday). `radiateurs_couverture` (both
  columns were added after the first version of the header, so readers by name keep working) is the share of
  the radiator-days up to `radiateurs_jusqu_au` that were fully measured, a 4-decimal fraction: below
  `1,0000` a radiator was not measured every one of those days. A radiator sum is whole for the row
  only when `radiateurs_couverture` is `1,0000` and `radiateurs_jusqu_au` is the row's last day.
  `reste_kwh` is given only when the radiators cover the whole bar.
  A counted day without Linky data keeps its `abonnement_eur`, with `total_eur` empty.
  `dehors_moy_c` (1 decimal) is the mean outdoor temperature of the row's elapsed days with weather, each day's
  mean being (Tmin + Tmax) / 2 of the Paris civil day; `dju_base18` (1 decimal) the sum of heating degree days
  base 18 °C (méthode météo), given only when every elapsed day has weather; `meteo_jours` the number of those
  days (an integer). All three are empty without a weather place (Réglages › Météo), and `dehors_moy_c` is empty
  when no elapsed day has weather. Appended after `radiateurs_couverture` (Plan 14), so readers by name keep
  working. The figures are Météo-France / Copernicus model output via Open-Meteo (CC BY 4.0), never a measurement
  at the home.
- `courbe_<date>.csv` — one row per interval of the Courbe's day (46, 48 or 50):
  `debut;fin;minutes;wh;w_moyen;part_hc;couleur_tempo;prix;eur;radiateurs_wh`. Wh and W are integers,
  `part_hc` a 4-decimal fraction, `prix` €/kWh and `eur` with 4 decimals; `couleur_tempo` is `bleu`, `blanc` or `rouge`
  (the colour of the half-hour's Tempo day: before 06:00, the previous day's), empty when the half-hour
  is not Tempo-priced or its colour is unknown. `radiateurs_wh` is empty unless every radiator was measured in
  that half-hour (never a partial sum).
- `pieces_<from>_<to>.csv` — the period's elapsed days (up to yesterday), as « Où part l’énergie » shows them;
  each room, then its radiators:
  `piece;radiateur;kwh;part;hc_kwh;hp_kwh;eur;temp_moy;consigne_moy;heures_chauffe;couverture;depuis`.
  `part` (rooms) and `couverture` (radiators) are 4-decimal fractions; `eur` is energy only; kWh, HC
  and HP are the API's 3-decimal figures (the table at 2 decimals allocates its rounding so rows add up). A
  room's kWh sums its radiators with a figure: its radiators' `couverture` says whether it is whole.
- `meteo_<from>_<to>.csv` (Plan 15, « Exporter météo et consommation (CSV) », offered with a weather place once
  « Météo et coût » has days; `<from>`/`<to>` are the model's 12-month window, `<to>` exclusive) — one row per day
  of that window with Linky energy and a complete weather day, by date:
  `date;dehors_moy_c;degres_sous_equilibre_c;kwh;energie_eur;retenu;motif;attendu_kwh`. `date` is the Paris day
  (`YYYY-MM-DD`); `dehors_moy_c` its outdoor mean (1 decimal); `degres_sous_equilibre_c` (1 decimal) the degrees
  below the model's balance point; `kwh` (3 decimals) the day's Linky kWh and `energie_eur` (2 decimals) the same
  energy € as its day bar (empty with an unknown Tempo colour or no tariff); `retenu` `1`/`0` whether the model used
  the day; `motif` empty, `absence` (a Kelvin absence touched the day) or `atypique` (left out as an outlier);
  `attendu_kwh` (3 decimals) the model's expected kWh for that day's temperature. `degres_sous_equilibre_c` and
  `attendu_kwh` are empty while the model is hidden. Every model figure is an estimate (Kelvin's model of measured
  data); the outdoor figures are Météo-France / Copernicus model output via Open-Meteo (CC BY 4.0). The Énergie
  file above is unchanged.
